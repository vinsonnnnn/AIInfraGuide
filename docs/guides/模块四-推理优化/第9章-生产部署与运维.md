## 本章简介

前面章节让推理服务"跑得又快又省"，本章解决"稳定地服务真实流量"的问题：如何打包、编排、观测、扩缩容和做容量规划。这是从 Demo 到生产的最后一公里，以 vLLM 部署为实例。

**容器化与 Kubernetes 部署** 讲清如何把 vLLM 服务打成镜像并在 K8s 上编排：GPU 资源请求、就绪/存活探针（注意模型加载耗时长，探针阈值要放宽）、镜像与权重的拉取策略，以及 vLLM Production Stack、KServe 等生产部署方案。

**可观测性** 是运维的眼睛：vLLM 暴露 Prometheus 指标端点（TTFT、TPOT、running/waiting 请求数、KV Cache 利用率、抢占次数等），配合 Grafana 看板和结构化日志，做到故障可定位、性能可追踪。

**自动扩缩容与负载均衡** 覆盖多副本部署下的请求分发：基于 QPS / 队列长度 / KV Cache 利用率的 HPA 扩缩容，以及前缀感知（Prefix-aware）路由如何把命中同一 System Prompt 的请求导向同一副本以提升缓存命中率。

⚠️ **安全提示**：vLLM 的 OpenAI 兼容服务默认不做认证，直接暴露到公网等于开放算力与数据。生产部署务必在网关层加上 API Key 校验、TLS 与网络隔离——本章会明确这一点，避免"裸奔"上线。

**容量规划**给出从 SLO 和峰值 QPS 反推所需 GPU 数量的方法：结合单副本压测得到的吞吐上限、显存约束和冗余系数，估算集群规模与成本。

## 新手学习路线

### 先把角色分清楚

镜像固定软件环境，模型快照固定权重与 Tokenizer；Pod 运行进程，Deployment 管副本，Service 提供入口。网关处理接入，Router 决定请求给谁，HPA 决定期望多少副本。指标与日志提供反馈，但不会自动替你把这些组件全部装好。

9.1 的自制全景图先给出这些路径，后面逐步解释。不要求一开始理解所有 Kubernetes 细节；先沿“一次请求如何进来、模型如何就绪、问题怎样被发现”阅读。

| 小节 | 学习目标 | 最小练习 |
|------|----------|----------|
| 9.1 部署 | 读懂 GPU、存储、端口、探针和更新 | 固定快照，验收一份副本 |
| 9.2 观测 | 知道慢在入口、队列、缓存还是执行 | 读取指标样本，区分三类指标 |
| 9.3 流量 | 路由、扩缩容、排空与访问控制协同 | 手算 HPA 比例，核对控制循环 |
| 9.4 规划 | 从 SLO 反推副本、GPU 与余量 | CPU 上计算吞吐和 KV 账本 |

### 区分实验清单与完整生产系统

本章以 vLLM v0.19.0 单 GPU 普通副本为起点，再解释多副本与多卡差别。Docker/Kubernetes 命令使用 Linux Bash；Kubernetes、Prometheus、指标适配器与存储均需在自己的实验环境准备。

清单中的路径、PVC、Secret 和自定义指标都有明确前置条件。语法通过不代表资源存在，Pod Ready 不代表业务 SLO 达标，HPA 提高期望数量也不代表新模型立即能接请求。每一步都要留下相应验证记录。

## 📝 总结

- 从固定身份、资源与真实生成开始验收部署。
- 指标、日志和短窗口 Trace 共同连接用户体验与系统状态。
- 路由、HPA、就绪和排空需要协同，不能只增加副本数字。
- 容量还需覆盖 KV、故障域、冷启动和发布，而不只是平均 QPS。

## 🎯 自我检验清单

- 能解释镜像、模型、Pod、副本和 GPU 的区别
- 能说明三类探针、服务就绪和业务达标分别证明什么
- 能读懂指标单位、分位数与副本采集范围
- 能说明 HPA 为什么需要适配指标、物理资源与启动时间
- 能为故障、缩容和长请求定义可检查的处理步骤
- 能按相同质量与负载计算健康副本、KV 和 GPU 小时
