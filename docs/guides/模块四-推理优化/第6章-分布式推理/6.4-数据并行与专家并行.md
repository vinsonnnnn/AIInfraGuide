## 1. Dense DP：不同请求交给不同副本

最直接的 Dense DP 是运行多个完整引擎，每个引擎有自己的权重、调度队列和 KV Cache，再由入口分发请求。副本内部也可以使用 TP/PP。

理想情况下，$d$ 个相同副本的容量可接近单副本的 $d$ 倍，但需要流量足够、请求分配均衡，且入口没有成为瓶颈。DP 通常不会缩短某一条请求在一个副本中的计算路径。

两卡、模型单卡装得下时，vLLM v0.19.0 的内部负载均衡入口可以写为：

```bash
CUDA_VISIBLE_DEVICES=0,1 vllm serve Qwen/Qwen2.5-7B-Instruct \
  --dtype half --data-parallel-size 2 --tensor-parallel-size 1 \
  --max-model-len 4096 --served-model-name dp-demo
```

这里 `--max-num-seqs` 等容量约束要按 DP Rank 理解。两个副本允许的总活跃请求数可能比单引擎更多，比较时既要报告单 Rank 参数，也要报告整体并发。

## 2. 轮询为什么还会分配不均

同样一条请求，可能是“你好”，也可能是八千 Token 输入加两千 Token 输出。只数请求数量，就像把一封信和一个集装箱都记为“一件”。

| 路由信号 | 能看到什么 | 盲区 |
|---|---|---|
| 轮询 / 最少连接 | 请求数或连接数 | 不知道长度与计算量 |
| Running/Waiting 数 | 引擎排队和活跃程度 | 请求大小仍不同 |
| Token/KV 预算 | 长请求和缓存压力 | 输出长度不完全可知 |
| 前缀命中信息 | 可复用的历史 KV | 过度亲和可能形成热点 |

引擎之间默认不共享物理 KV。把同一会话路由回原副本可能增加前缀命中，但必须和负载平衡共同考虑；“总去命中最多的副本”也可能把那里压垮。

## 3. MoE：总参数与激活参数要分开算

MoE 每个 Token 通常只选择少数专家参与计算，所以单 Token 激活参数可以少于总参数。**未被当前 Token 选中的专家仍要存放，不能用激活参数代替权重容量。** 共享专家、Attention、Router 和其他 Dense 层也要单独核算。

EP 将专家分配到不同 Rank。一次专家层大致经历：

```mermaid
graph LR
    A["本地 Token 与路由分数"] --> B["Dispatch：送往专家所在 Rank"]
    B --> C["各 Rank 执行本地专家"]
    C --> D["Combine：返回并按权重合成"]
    D --> E["恢复 Token 顺序与后续层"]
```

Dispatch/Combine 常被概括为 All-to-All，但实际后端可能使用 AllGather/ReduceScatter 或专用稀疏通信。不能只从论文术语推断实际 NCCL 调用了哪个原语。

## 4. DP+EP 的 Rank 到底怎样组合

按 vLLM v0.19.0 的组织，启用 `--enable-expert-parallel` 后，专家层的 EP 组大小为 TP×DP；Attention 层仍按每个 DP 组内的 TP 规则处理。

例如 TP=2、DP=4，总计八卡：Attention 是四组两卡 TP；专家层可跨八个 Rank 分布。它不是“八卡乘 EP=8，再要六十四卡”。本例不加入 PP；其他组合先查模型与版本支持。

更重要的是，MoE 的这些 DP Rank 可能仍须对齐前向、一起参与专家通信。某个 Rank 没有真实请求时也可能需要空前向来协同。不能把它们当成可随意独立启停的 Dense 副本。

## 5. 专家热点与通信账本

假设一次专家层共处理 $T$ 个 Token，每个选择 $k$ 个专家，隐藏维度 $H$、元素字节数 $b$。只看一次 Dispatch 的未压缩载荷量级：

$$
S_{\text{dispatch}}\sim T k H b
$$

Combine 也要回传结果。真实跨网卡字节数取决于本地命中、Token 复制、通信压缩、共享专家与后端实现，不能直接把这个量级当成全部网络流量。

把专家接收的 Token 数记为 $c_e$，一个简单均衡指标是：

$$
\text{Balancedness}=\frac{\operatorname{mean}(c_e)}{\max(c_e)}
$$

即便平均负载不高，最热专家或最忙 Rank 也可能拖住同步组。分析时应同时看专家计数、Rank 汇总和链路排队。

## 6. 动手观察：同样 Token 总数，热点代价不同

```python
def balancedness(counts):
    assert counts and all(c >= 0 for c in counts)
    return 1.0 if max(counts) == 0 else sum(counts) / len(counts) / max(counts)

even = [25, 25, 25, 25]
skew = [70, 10, 10, 10]
print("均匀:", balancedness(even), "偏斜:", balancedness(skew))
assert sum(even) == sum(skew)
assert balancedness(skew) < balancedness(even)

# 假设两张卡，分别持有两个专家。
rank_load = [sum(skew[:2]), sum(skew[2:])]
print("每 Rank Token 数:", rank_load)
assert rank_load == [80, 20]
```

这是计数模型，不含专家批次的非线性效率。真实服务还要观察热点是否持续，避免为了短暂波动频繁搬移专家。

## 7. EPLB 与通信后端的选择

EPLB 可以调整专家映射，并通过冗余专家改善热点。它有额外权重存储和迁移成本，省下的执行时间必须大于这些代价。不要把“打开负载均衡”理解为免费消除所有不均衡。

在已有兼容 MoE checkpoint、足够显存与依赖的前提下，一个两卡示意入口为：

```bash
CUDA_VISIBLE_DEVICES=0,1 vllm serve /models/moe-checkpoint \
  --tensor-parallel-size 1 --data-parallel-size 2 \
  --enable-expert-parallel --all2all-backend allgather_reducescatter
```

这里的本地路径是占位符，不代表任意 MoE 都能用两卡装下。先跑目标版本的通用可行路径，再比较 DeepEP 等后端的依赖、硬件要求和场景；Prefill 偏吞吐、Decode 偏延迟，不能只按名字选一个后端覆盖全部请求。

## 📝 总结

- Dense DP 复制引擎分请求，容量扩展依赖负载均衡。
- MoE 的激活参数少，不代表所有专家权重都不用存。
- EP 在专家层路由 Token，通信与热点共同影响同步步长。
- DP+EP 中的 DP Rank 不一定完全独立，EPLB 也有显存与迁移成本。
