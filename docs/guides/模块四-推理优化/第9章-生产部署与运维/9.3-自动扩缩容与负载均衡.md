餐厅有三个窗口，却把所有顾客都叫到同一个窗口，增加窗口也没用；等队伍排满才通知新厨师上岗，新厨师又可能赶不上这一波。路由决定**已有资源怎么分工作**，扩缩容决定**未来需要多少资源**，两者需要互相配合。

本节沿用普通 Dense 多副本场景。一个副本内部可以多卡协作，不能把 HPA 副本数、TP 卡数和第六章 MoE 的 Token Router 混成同一个概念。

## 1. 网关、Router、HPA 分别做什么

| 组件 | 主要工作 | 决策时间尺度 |
|------|----------|--------------|
| 网关 | 接入、身份校验、配额、TLS 和外部协议 | 每次连接或请求 |
| Router | 选择哪个兼容副本处理请求 | 每次请求及状态变化 |
| HPA | 根据指标调整工作负载期望副本数 | 周期性控制，不是每请求即时决策 |
| 调度器/Deployment | 创建 Pod、安排资源、等待就绪 | 从秒到模型冷启动所需时间 |

### 1.1 这些角色可能合在一个产品里

实现可以把网关和 Router 合并，也可能外置多个组件。学习时先看职责，不要仅凭某个软件名字判断它已经提供所有能力。

HPA 增加副本后，仍需有空闲 GPU、镜像、模型和存储；没有物理资源时，期望数量增长也只会产生 Pending Pod。

### 1.2 Kubernetes Service 不等于模型感知路由器

普通服务入口提供网络发现与转发，不会天然知道输入 Token 数、KV 余量或某个前缀在哪份副本。HTTP Keep-alive、流式连接和具体代理的分发策略也会影响流量分布。

若需要按模型状态分配，应由能获取这些信息的组件实现。单纯部署两个 Pod，不能证明每类工作都已均衡。

## 2. 选择副本时，到底在看什么

### 2.1 从轮询走到工作量

轮询主要均衡分配次数；最少未完成请求主要比较数量；Running/Waiting 反映引擎拥挤程度；Token 长度和 KV 余量进一步描述工作与容量。它们各有局限，详细例子见 6.4。

一个长文档与一句问候都叫“一条请求”，成本却可能相差很大。连接少的副本也可能正在运行一个超长输入；连接多的副本可能只是复用或等待网络。不要把最少连接直接等同于最短等待时间。

### 2.2 先筛兼容，再权衡快慢

先排除未就绪、模型/版本不兼容或无法接纳的副本，再综合排队、未命中 Prefill、KV 和预期输出等信息。状态上报会过期，输出长度也未知，因此路由是基于观测的估计，不是精确预言。

短时倾斜还可能来自请求本身，先检查流量和观测延迟，再决定是否修改策略。

## 3. 前缀感知路由：复用能省什么，不能省什么

### 3.1 命中需要精确兼容的历史

新请求若以相同 Token 前缀开头，且副本保留了可用 KV，就可能减少重复 Prefill。相同会话 ID、主题类似或都用了“客服助手”几个字，并不保证精确命中；模型、模板和其他状态也必须兼容。

独立副本不会因为权重一样就自动共享物理 KV。前缀亲和倾向把可复用请求送回合适位置，但新副本刚启动时通常还没有相同热缓存。

### 3.2 命中最多，也可能等得最久

假设 A 有可复用前缀，排队 150 ms、剩余 Prefill 20 ms；B 没命中，排队 10 ms、Prefill 80 ms。暂时忽略其他相同成本，A 合计 170 ms，B 为 90 ms。

这些是假设数字，说明缓存收益必须与排队一起比较。一直选 A 会制造热点，亲和不应变成无条件绑定。Prefix Cache 主要减少输入计算，也不能直接消掉后续 Decode。

### 3.3 扩容后为什么没有立刻均匀

旧副本有热缓存、新副本冷启动，过强亲和可能让新副本接不到足够工作。控制器与 Router 需要考虑冷/热状态、容量与逐步导流，不能只以 Pod 数量判断有效容量已经翻倍。

## 4. HPA 怎样从指标算出副本数

### 4.1 用一个小例子理解比例控制

假设两个 Pod 的等待队列是 3 和 9，平均为 6；目标平均等待数为 4。基础比例计算会建议 $\lceil2\times6/4\rceil=3$ 个副本。

这只是算法直觉。实际 HPA 还会处理容差、指标缺失、就绪、上下限、稳定窗口和变化速率，不保证下一时刻恰好出现三个可用副本。

QPS、队列、KV 或 GPU 指标都能提供不同信息，不能只看 GPU 活动：低利用率可能是没有请求，也可能在等数据；KV 高可能是长上下文而非计算忙。应按阶段瓶颈选信号，并结合 SLO。

### 4.2 自定义指标不是直接写一个 PromQL

HPA 从 Kubernetes 指标 API 取数，不会直接抓 `/metrics`。下面示例要求已经安装并配置指标适配器，将每个 Pod 的等待数暴露为 **`vllm_waiting_requests`**，每 Pod 一份、语义一致。

这个名字是适配后的教学名称，不是 vLLM 自动注册到 Kubernetes 的原始指标。普通 metrics-server 也不会自动把任意 Prometheus 指标变成它。

### 4.3 一份有前置条件的 HPA

保存为 `vllm-hpa.yaml` 前，确认目标 Deployment、GPU、PVC 多副本访问与适配器都已满足条件。这里最少两副本，会改变 9.1 的单副本实验规模：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: vllm-demo
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: vllm-demo
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Pods
      pods:
        metric:
          name: vllm_waiting_requests
        target:
          type: AverageValue
          averageValue: "4"
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Pods
          value: 1
          periodSeconds: 60
```

上行允许较快增加，下行先观察再逐步减少，用于避免频繁抖动；这些值不是任意服务的最佳参数。指标缺失时先检查 HPA conditions、适配器和目标身份，而不是把空值当零队列。

## 5. 冷启动、背压和缩容必须一起设计

### 5.1 新副本来不及救已经超时的请求

假设现有能力 10 请求/s，突然来到 20 请求/s，新增副本需要 90 秒就绪。在完全无拒绝、取消且能力不变的简化模型中，期间会多积压约 $(20-10)\times90=900$ 条工作。扩容成功也不能让已经等超时的用户“重新没等过”。

因此需要基础余量、可能的预测预热、有界队列和准入。队列不是无限免费空间，maxReplicas 也不创造物理 GPU；达到上限时要有明确过载处理。

### 5.2 缩容前先排空，不是直接杀进程

```mermaid
graph LR
    A["选定待退出副本"] --> B["停止分配新请求"]
    B --> C["等待既有流式请求完成或按契约结束"]
    C --> D["确认取消、缓存与传输清理"]
    D --> E["停止进程并回收资源"]
```

readiness、路由摘除、连接传播和进程退出之间存在时间差。只给 `preStop` 加固定 sleep，不能保证任意长请求已完成；`terminationGracePeriodSeconds` 也只是退出时间预算，不是无限保活。

流式输出到一半后，自动重试可能重复生成或改变答案。需要区分尚未开始的可重试请求与已经输出的请求，定义请求身份、取消传播及失败响应，不可简单对所有错误无限重试。

## 6. 接入认证、TLS 与网络边界

### 6.1 有入口，不代表已经有访问控制

原提纲强调生产入口必须有认证与隔离。vLLM 支持 API Key 配置；v0.19.0 也可读取 `VLLM_API_KEY`。网关还应根据服务需要提供 TLS、身份/配额、输入和输出上限、超时与流式转发策略。

假设已有 Secret `vllm-api-key`，其中键为 `api-key`，可把以下片段合并到 9.1 的容器定义，而不是把它单独当成完整 Kubernetes 对象提交：

```yaml
env:
  - name: VLLM_API_KEY
    valueFrom:
      secretKeyRef:
        name: vllm-api-key
        key: api-key
```

Secret 的创建和轮换按环境的凭据管理方式完成，不把真实密钥写进 Git 或笔记。Base64 不是加密；还要配置访问权限和存储保护。修改 Secret 后如何生效也要考虑环境变量的进程生命周期，不能假设已有进程自动重读。

### 6.2 分别管理数据与诊断入口

推理接口、`/metrics` 和 Profiler 等管理端点具有不同用途，单个 API Key 设置不应被当作所有路径都已隔离的证明。网关按路径控制，后端与监控保留在所需网络范围内。

Kubernetes NetworkPolicy 还依赖网络插件支持，且隔离网络连接与校验应用身份是不同层次。TLS 负责传输保护，也不等于配额与租户授权已完成。

### 6.3 请求配额应考虑 Token 工作量

相同 QPS 下，长输入、长输出和短问答消耗不同资源。可以按模型、租户、输入长度、最大输出、并发和速率设置合理约束，同时把拒绝和超时纳入统计。

网关缓冲还可能让服务端出字流畅、客户端却成段收到。验收要同时验证认证失败、正常流式输出、取消、超限和服务端不可用路径，不能只测试一次 HTTP 200。

## 7. 新手怎样验证这套控制循环

先用两份固定副本检查分流与原始指标，再用有限负载观察队列；确认自定义指标 API 的实际值，最后启用 HPA。记录“期望数、Running 数、Ready 数、有效接流量数”，它们可能不同。

然后在实验环境增加负载并观察：何时出现扩容建议，新 Pod 何时就绪，旧请求是否仍达标，流量是否分过去。缩容时检查已开始的流式请求。每个阶段都能解释，再去增加前缀感知等更复杂策略。

## 📝 总结

- Router 分配现有工作，HPA 调整未来副本，两者不是同一个决策。
- 前缀命中需要与队列、冷启动和兼容性一起权衡。
- HPA 自定义指标需要适配器与正确的每 Pod 语义。
- 有界准入、排空、身份、TLS 和网络边界共同决定服务能否稳定接入。
